# initview.cloud QA 수정 변경 기록 (2026-10)

운영 서비스(https://initview.cloud) QA에서 나온 문제를 고치면서 **이전과 달라진 동작**을 모두 적은 문서다.
발표·리뷰에서 "무엇이, 왜, 어떻게 바뀌었는지"를 설명할 때 이 문서를 기준으로 한다.

| 2차: AI 면접 QA 높음 항목 | 10/29 노트북 AI 면접 QA(답변 7개 제출) | 이 문서와 같은 커밋 (dev, 미푸시) |

## 1차: 웹페이지 QA 높음 항목 (`52ae50a3`)

### 1-1. 로그인 없이 공고 상세 보기
- **이전:** `/candidate/jobs/{id}`는 지원자 로그인이 필요했다. 비로그인 방문자는 공고 내용을 보기 전에 로그인 화면으로 이동했다.
- **이후:** 로그인 없이도 공고 상세, 회사 소개, 근무지, 비슷한 공고를 볼 수 있다.
- **어떻게:**
  - 공개 API `GET /api/v1/public/jobs/{jobId}`(API-059A)를 추가했다. 계약 문서 `api-index.md`와 `api-spec.md`를 먼저 고쳤다.
  - 공개 응답의 `canApply`는 항상 true, `alreadyApplied`는 항상 false다. 개인별 정보가 없기 때문이다.
  - 프론트 라우트 정책에 `optional` 종류를 새로 만들었다. 이 종류는 비로그인을 허용하고, 기업 계정으로 들어오면 기업 화면으로 보낸다.
- **파일:**
  - `public-candidate.controller.ts`, `candidate.service.ts`(`getPublicJobDetail`), `candidate.routes.ts`
  - `routePolicy.ts`, `CandidatePages.tsx`, `api.ts`

### 1-2. 없는 공고 요청 시 404
- **이전:** 공개 API로 없는 공고를 요청하면 500 "서버 오류가 발생했습니다."가 났다.
- **이후:** 404 `COMMON_NOT_FOUND`와 "지원 가능한 채용공고가 아닙니다."를 돌려준다.
- **어떻게:** 공개 컨트롤러에 도메인 오류(`CandidateDomainError`)를 HTTP 오류로 바꾸는 `handle()`을 붙였다. 지원자용 컨트롤러와 같은 방식이다.
- **참고:** 1차 로컬 검증 중에 발견해서 같이 고쳤다.

### 1-3. 로그인 후 원래 화면으로 복귀(`next`)
- **이전:** 로그인이 필요한 화면에 비로그인으로 들어가면 로그인 화면으로 갔다. 로그인 후에는 항상 기본 화면(지원자는 공고 목록, 기업은 채용 관리)으로 이동해서, 보던 화면을 다시 찾아가야 했다.
- **이후:**
  - 보호 화면에 접근하면 `/login?next=<원래 경로>`로 이동한다. 로그인하면 그 경로로 돌아온다.
  - 비로그인으로 "지원하기"를 누르면 `/login?next=/candidate/jobs/{id}?apply=1`로 이동한다. 로그인하면 같은 공고로 돌아오고 지원서 작성 창이 바로 열린다.
  - 기업 화면도 같다. `/company/login?next=…`로 이동한 뒤 로그인하면 원래 화면으로 돌아온다.
  - Google 로그인에도 적용된다. 로그인 시작 전에 `next`를 sessionStorage에 저장하고, 콜백에서 꺼내 쓴다.
- **안전장치(`resolvePostLoginPath`):** 아래 경우에는 `next`를 무시하고 기본 화면으로 보낸다.
  - `/`로 시작하지 않는 경로
  - `//` 또는 `/\`로 시작하는 경로(외부 사이트로 보내는 공격 방지)
  - 공개 화면 경로
  - 로그인한 역할과 다른 역할의 화면 경로
- **파일:** `routePolicy.ts`, `AuthProvider.tsx`, `AuthForms.tsx`, `app/auth/google/callback/page.tsx`

### 1-4. 직접 로그아웃할 때는 `next`를 붙이지 않음
- **이전(1-3을 적용한 직후):** 보호 화면에서 로그아웃하면 `/login?next=/candidate/billing`처럼 `next`가 붙었다. 로그아웃 이동보다 보호 화면 검사가 먼저 실행되기 때문이다.
- **이후:** 사용자가 직접 로그아웃하면 `next` 없이 원래처럼 `/login` 또는 `/company/login`으로 간다. 세션이 만료돼서 로그아웃된 경우에는 `next`가 붙는다.
- **어떻게:** `AuthProvider`에 `explicitLogoutRef`를 두었다. 로그아웃할 때 true, 로그인할 때 false로 바꾸고, 보호 화면 검사에서 이 값을 확인한다.
- **참고:** 1차 로컬 검증 중에 발견해서 같이 고쳤다.

### 1-5. 모바일 가로 넘침
- **이전:** 375px 폭 휴대폰에서 공고 목록 페이지 폭이 873px로 늘어났다. 화면이 옆으로 밀렸다.
- **이후:** 페이지 폭이 375px로 유지된다. 직무 바로가기는 페이지 전체가 아니라 카드 줄 안에서 가로로 넘긴다.
- **어떻게(`globals.css`):**
  - `.candidate-jobs-panel`과 `.candidate-jobs-all`에 `grid-template-columns: minmax(0, 1fr)`을 넣었다. 그리드 칸이 내용물 최소 폭만큼 늘어나는 것을 막는다.
  - 900px 이하에서는 마지막 상단 메뉴의 드롭다운을 오른쪽 정렬했다(`right: 0`). 드롭다운이 화면 밖으로 나가지 않는다.

### 1-6. 상단 메뉴에서 "지표" 제거
- **이전:** 지원자 마이페이지 메뉴와 기업 상단 메뉴에 "지표"(`/ai/performance`)가 보였다. 이 화면은 내부 모니터링용이다.
- **이후:** 두 메뉴에서 모두 뺐다. 화면 자체는 남아 있어서 주소를 직접 입력하면 열린다. (#436)
- **파일:** `candidate-nav-config.ts`(+spec), `CompanyRecruitingChrome.tsx`

### 1-7. 문구 변경
| 위치 | 이전 | 이후 |
| --- | --- | --- |
| Google 로그인 불가 시 서버 메시지 | Google OAuth 환경변수가 설정되지 않았습니다. | 현재 Google 로그인을 사용할 수 없습니다. 이메일로 로그인해 주세요. |
| 지원자 결제 화면 버튼 | 테스트 이용권 5회 추가 | 체험용 이용권 5회 받기 |
| 위 버튼 성공 알림 | 테스트용 모의면접 이용권 5회를 추가했습니다. | 체험용 모의면접 이용권 5회를 받았습니다. |
| 위 버튼 실패 알림 | 테스트 이용권을 추가하지 못했습니다. | 체험용 이용권을 받지 못했습니다. |

### 1-8. 로컬 시드 기업 프로필
- **이전:** `Local development company profile.` 등 영어 개발용 문구였다.
- **이후:** 한국어 데모 문구로 바꿨다. 예: "INIT 데모용 기업입니다. AI 면접 기반 채용 흐름을 체험할 수 있도록 샘플 공고를 운영합니다."
- **주의:** 시드는 처음 만들 때만 값을 넣는다(create-only upsert). 그래서 이미 데이터가 있는 운영 DB는 바뀌지 않는다. 운영 기업 프로필은 여전히 영어 문구이고, 기업 화면에서 직접 고쳐야 한다.

## 2차: AI 면접 QA 높음 항목

### 2-1. 동의 체크박스가 처음부터 체크되어 나오던 문제
- **QA 현상:** 면접 안내 3/3 화면의 필수 동의 3개(개인정보 수집·이용, 이력서/포트폴리오 AI 분석, AI 면접 녹화·녹음)가 처음부터 체크되어 있었다.
- **원인:**
  - 지원서 작성 폼의 기본값이 동의 3개를 모두 체크한 상태였다(`defaultApplicationFormState.consentTypes`). 2026-07-23 `04f051bd` "지원서 제출 필수 동의 항목을 기본 선택 처리"에서 일부러 넣은 동작이다.
  - 지원서를 제출하면 이 동의가 저장된다. 면접 안내 화면은 "이미 동의함"(`consentCompleted`, #288)으로 보고 체크박스를 채워서 보여 준다.
  - 결국 지원자는 한 번도 직접 체크하지 않았는데 동의한 것으로 기록됐다.
- **이전:** 지원서 폼과 면접 안내 화면 모두 처음부터 체크된 상태였다.
- **이후:**
  - 지원서 폼의 동의는 모두 해제된 상태로 시작한다. 지원자가 직접 3개를 체크해야 제출 버튼이 켜진다. 폼에는 "0 / 3 완료"로 표시된다.
  - 면접 안내 화면의 동작(#288)은 그대로다. 이미 직접 동의한 사람은 다시 체크하지 않아도 된다.
- **왜:** 개인정보 수집·이용 동의는 정보주체가 직접 선택해야 한다. 미리 체크된 동의는 명시적 동의로 보기 어렵다.
- **영향:** 지원서 제출 단계에서 클릭이 3번 늘어난다. `04f051bd`의 편의 목적을 되돌리는 변경이라 D 담당자 리뷰가 필요하다.
- **파일:** `view-model.ts`(`defaultApplicationFormState`), `contract.spec.ts`

### 2-2. 마이크 입력 0%인데 "적정합니다"로 통과되던 문제
- **QA 현상:**
  - Steam 가상 마이크(소리가 들어오지 않는 장치)로 입력이 0%였는데도 마이크에 체크 표시가 붙었다. "카메라 밝기, 마이크 입력, 네트워크 상태가 적정합니다"가 나왔다.
  - 실제 신호는 최대 57%였는데 화면 표시는 1%에 멈춰 있었다.
- **원인:**
  1. 통과 판정이 "마이크 트랙이 연결돼 있는가"(`isMicrophoneTrackReady`)만 확인하고 측정값을 쓰지 않았다. 2026-07-04 `d6d817a8` "마이크 입력 경고로 면접 진입 막히지 않도록 수정"에서 일부러 완화한 결과다.
  2. 측정용 `AudioContext`를 버튼 클릭 뒤 await를 여러 번 거친 다음 만든다. 그래서 Chrome에서 `suspended` 상태로 남아 실제 소리가 있어도 무음으로 읽힐 수 있었다. 1% 고정 현상의 유력한 원인이다.
- **이전:** 무음이어도 면접을 시작할 수 있었다. 그러면 답변이 무음으로 녹음될 수 있었다.
- **이후:**
  - 소리가 전혀 없을 때(피크 5% 이하)만 "면접 시작"을 막는다. 화면에는 "마이크 입력이 감지되지 않았습니다. 테스트 문장을 소리 내어 읽어주세요."가 나온다.
  - 입력이 작거나(20% 미만) 너무 큰(85% 초과) 것은 지금처럼 경고만 하고 막지 않는다. `d6d817a8`의 의도는 유지했다.
  - 1.8초 점검 중에 말하지 못했더라도 다시 누를 필요가 없다. 실시간 미터가 소리를 감지하는 순간 자동으로 통과로 바뀌고, "음성 입력이 감지되었습니다"가 표시된다.
  - 측정과 실시간 미터를 시작할 때 `AudioContext`가 `suspended`이면 `resume()`한다. 면접 중 마이크 미터에도 같이 적용했다.
- **범위:** 무음 차단은 면접 시작 전 안내 화면에만 적용했다. 면접 진행 중에 장치를 다시 점검할 때는 막지 않는다. 면접 도중 지원자가 갇히는 것을 피하기 위해서다.
- **파일:** `CandidatePages.tsx`
  - `handleDevicePreview`
  - `startGuideMicrophoneMeter`
  - `startMicrophoneMeter`
  - `measureMicrophoneQuality`
  - `formatMicrophoneQualityStatus`
  - `hasMicrophoneInput`, `resumeAudioContext`(신규)

### 2-3. 답변 시간이 녹화 시작 전부터 줄어들던 문제
- **QA 현상:** "질문 음성이 나오는 동안에도 남은 시간이 줄어든다", "Q1이 시간 초과로 자동 제출됐다"는 보고가 있었다.
- **로그 재확인 결과:**
  - 질문 음성이 나오는 동안에는 원래 타이머가 멈춘다(`questionSpeechPlaying`). 이 부분은 오해였다.
  - Q1이 시간 초과된 것은 QA 도구 쪽 원인이었다. 녹화가 01:30에서 시작됐지만, QA 쪽에서 답변 음성을 29초 늦게 틀었다.
  - 실제 문제는 따로 있었다. 녹화가 시작되는 시점에 이미 남은 시간이 01:21, 01:24, 01:27인 문항이 있었다. 녹화를 실제로 시작하기 전부터 시간이 3~9초 줄어든 것이다.
- **원인:** 녹화를 시작할 때 실시간 STT 연결(`startRealtimeSttRelayForRecording`)과 카메라 재연결을 기다린다. 그 대기 시간 동안에도 카운트다운이 돌았다.
- **이전:** 녹화가 시작되기 전 준비 시간만큼 답변 시간이 깎였다.
- **이후:** 녹화 시작 준비 중(`recordingStarting`)에는 카운트다운과 시간 초과 처리를 멈춘다. 녹화가 실제로 시작되거나 시작에 실패하면 다시 돈다.
- **파일:**
  - `view-model.ts`: `InterviewRuntimeCountdownInput.recordingStarting`, `shouldRunInterviewRuntimeCountdown`
  - `CandidatePages.tsx`: `handleStartRecording`를 감싸는 함수와 `startRecordingForCurrentQuestion`
  - `contract.spec.ts`

### 2차에서 아직 고치지 않은 면접 QA 항목
| 우선순위 | 항목 |
| --- | --- |
| 중간 | 드롭다운에서 마이크를 바꿔도 처음에는 반영되지 않음 |
| 중간 | 결과 페이지 제출일이 실제 완료 시각과 다름 |

| 낮음 | 실시간 자막/인식 결과가 지원자에게 보이지 않음 |
| 낮음 | 맥락 없이 나온 질문(Q5) |

마이크 레벨 1% 고정은 2-2의 `resume()` 처리로 함께 해결될 것으로 본다. 실제 장치에서 다시 확인해야 한다.
